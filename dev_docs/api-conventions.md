# S3Forge API Conventions & Design Standards

This document describes the API design conventions, response envelopes, validation requirements, and storage rules enforced across the S3Forge platform.

---

## API Base Path & Versioning

- **Base URL**: `/api/v1`
- **Versioning Rule**: All endpoints are mounted under versioned path prefixes (`/api/v1/storage/buckets`). Breaking changes to request parameters or response envelopes require incrementing the URL version segment (e.g. `/api/v2`).

---

## Response Envelope Conventions

All API responses follow a uniform JSON structure produced by the helper functions in `apps/api/src/lib/response.ts`:

- **Success Envelope**:
  Contains a `status` indicator set to `"success"`, a human-readable `message`, a payload under `data`, and optional pagination metadata (`meta`) for list operations.
- **Error Envelope**:
  Contains a `status` indicator set to `"error"`, a high-level `message`, a machine-readable error `code` (e.g. `BAD_REQUEST`, `NOT_FOUND`, `CONFLICT`), and an optional `errors` array listing specific field-level validation issues.

---

## Storage & Bucket Conventions

### 1. Multi-Tenant Bucket Naming Strategy
To support multiple organizations while preventing global naming collisions inside MinIO:
- **User-Facing Name**: The bucket name provided by the user in API requests. This name must be unique within that organization's account.
- **Internal MinIO Name**: The actual bucket name created inside the MinIO engine, generated by prepending the organization prefix (e.g. `org1-bucket-name`). This ensures global uniqueness across all tenants in MinIO.

### 2. S3 Naming Rules
Bucket names validated by `apps/api/src/validators/storage.validators.ts` must follow standard S3 naming constraints:
- Length must be between 3 and 63 characters.
- Must contain only lowercase letters, numbers, hyphens, and dots.
- Must begin and end with a letter or number.

### 3. Soft Deletion Policy
When a bucket is removed via `DELETE /api/v1/storage/buckets/:name`:
- The bucket row in PostgreSQL is marked with `is_deleted = true`.
- Object metadata, audit logs, and historical usage statistics are preserved in the database for compliance.
- Soft-deleted buckets are automatically filtered out from standard list endpoints.

---

## Validation & OpenAPI Registration Workflow

1. **Zod Validator Schemas**: Defined in `apps/api/src/validators/`. Schemas decorate fields with descriptive metadata for OpenAPI generation.
2. **OpenAPI Path Registration**: Defined alongside route files in `apps/api/src/routes/`. Each path is registered with `openApiRegistry` in `apps/api/src/config/swagger.ts`.
3. **Route Middleware Integration**: Routes attach the generic `validate` middleware (`apps/api/src/middleware/validate.ts`), passing Zod schemas for `body`, `query`, or `params`. Request handling only reaches the controller if validation passes.
